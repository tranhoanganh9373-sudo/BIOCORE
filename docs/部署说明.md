# BIOCore 部署说明

## 1. 环境要求

- **Node.js** ≥ 20 LTS
- **pnpm** ≥ 8 (通过 corepack 启用)
- **InfluxDB** 2.7+ (本机或远程,见 `.env` 配置)
- **Ollama** (可选,用于本地 LLM)
- **PLC** (S7-200 SMART G2 或兼容设备,生产模式必须)

## 2. 安装与初始化

```bash
git clone <repo>
cd biocore
corepack pnpm install
cp .env.example .env  # 根据下方说明配置
mkdir -p packages/server/data
```

## 3. 关键环境变量

| 变量 | 开发默认 | 生产必须 | 说明 |
|---|---|---|---|
| `INFLUX_URL` | http://localhost:8086 | 真实 InfluxDB URL | 时序数据库连接 |
| `INFLUX_TOKEN` | (空) | **必填** | InfluxDB All-Access Token |
| `INFLUX_ORG` | BIOCore | 改为生产 org | |
| `INFLUX_BUCKET` | BIOCore_Data | 改为生产 bucket | |
| `JWT_SECRET` | biocore-dev-secret-... | **必填强随机** | 生成: `openssl rand -base64 32` |
| `AUTH_ENABLED` | true | true | 生产必须 true,否则无 token 自动 admin |
| `MOCK_PLC` | **true** | **false 或删除** | true 时所有 PLC 读取返回模拟值 |
| `API_V0_DEPRECATION_DATE` | 启动日+180 天 | 自定义 | 旧 /api/* 路径下线日期,过此日期可移除 v0 双挂载 |

## 4. 启动顺序

```bash
# 1. 确保 InfluxDB 已运行
curl http://localhost:8086/health  # 期望 200 OK

# 2. 启动 server (会自动跑 schema migrations)
cd packages/server
corepack pnpm exec tsx watch src/index.ts

# 3. 启动 web-ui
cd packages/web-ui
corepack pnpm exec next dev --port 3000
```

启动日志关键检查项:
- `[INFO] [Influx] 已连接 ...` — InfluxDB 连接 OK
- `[Migrator] 所有 N 个 migration 已是最新` — schema 同步 OK
- `[INFO] [API] V0 兼容期截止日期: ...` — 旧路径下线日期
- **如果看到 `⚠ MOCK_PLC=true 模式启用` 警告框,生产环境必须立即停服改 .env**

## 5. 生产部署 Checklist

### 5.1 MOCK_PLC 必须禁用
```bash
# .env 中改为
MOCK_PLC=false
# 或直接删除该行
```
开机后启动日志中**不应**出现红色警告框。

### 5.2 PLC 实机连接
- 通过 `/settings/plc-config` 添加真实 PLC 连接(S7 协议 + IP + Rack/Slot)
- 注意 `SetConnectionType(3)` 必须设置(代码已自动)
- 通过"测试连接"按钮验证可达
- 启动心跳监控

### 5.3 默认 admin 密码
首次启动会自动创建 `admin / admin123` 用户。**生产部署后必须**:
1. 用 admin/admin123 登录
2. 进入 `/settings/users` 修改 admin 密码为强密码
3. 创建其他用户分配角色 (engineer/operator/viewer)

### 5.4 API Key 创建
为 MES 等外部系统创建专用 API Key:
1. 登录后进入 `/settings/api-keys`
2. 点击"创建 API Key",填名称(例: `mes-prod`)
3. **立即复制 raw key**(只显示一次),保存到 MES 系统的环境变量
4. MES 调用 biocore 时:
   ```
   curl -H "X-API-Key: ak_xxx.xxxxx" http://biocore-host:3001/api/v1/reactors
   ```

### 5.5 数据备份
SQLite 数据库位于 `packages/server/data/biocore.db`。建议:
- 通过 `/settings/data-maintenance` 手动备份
- 或定期 `cp data/biocore.db data/backups/$(date +%Y%m%d).db`

### 5.6 反向代理 + TLS
生产环境应通过 nginx/Caddy 反向代理:
```nginx
# 例: Caddy
biocore.example.com {
  reverse_proxy /api/* localhost:3001
  reverse_proxy /ws localhost:3001
  reverse_proxy localhost:3000
}
```
WebSocket 协议使用 `wss://` (Caddy 自动处理 TLS)。

## 6. 常见问题

### 服务启动失败 "[Migrator] 致命错误"
- 检查 `packages/server/data/biocore.db` 文件权限
- 检查 `packages/server/migrations/` 目录可读
- 删除 `data/biocore.db` 后重启可全新初始化(数据全失!)

### "MOCK_PLC=true 模式启用" 警告
- 开发/演示阶段正常,**生产必须移除**

### Swagger 文档 `/api/v1/docs` 404
- 检查 swagger-jsdoc 和 swagger-ui-express 是否安装
- 检查 `apis: [__filename]` 路径正确

### WS 鉴权失败 close 1008
- 检查 `?token=` 或 `?api_key=` 是否传入
- token 是否过期(JWT 默认 24h)
- API Key 是否被撤销

### 旧 /api/* 路径仍能调用
- 这是正常的 6 个月兼容期,响应头会有 `Deprecation: version="v0", sunset="<日期>"`
- 兼容期到期后,在 `server/src/index.ts` 移除 `app.use('/api', ...)` 即可下线

## 7. 硬件规格矩阵（Sprint 4 Track A 加固）

| 档次 | CPU | RAM | 磁盘 | 适用场景 | OOM 阈值（auto = RAM × 20%）|
|---|---|---|---|---|---|
| **入门** | 4 核 | 8 GB | 256 GB SSD | 1-2 反应器，无本地 AI | ~1.6 GB |
| **标准** | 8 核 | 16 GB | 512 GB SSD | 多反应器 + 本地 Ollama AI | ~3.2 GB |
| **企业** | 16+ 核 | 32 GB+ | 1 TB+ NVMe | 多车间 / 中央汇总 | ~6.4 GB |

OOM 阈值由 `BIOCORE_OOM_THRESHOLD_MB` 控制：
- `auto`（默认）= 物理 RAM × 20%
- 也可填具体 MB 数（如 `1638`）覆盖

进程稳态目标：BIOCore 内核（不含 InfluxDB / Ollama）= 200-400 MB RSS。

## 8. 运维加固环境变量（追加到 .env）

| 变量 | 默认 | 说明 |
|---|---|---|
| `NODE_OPTIONS` | `--max-old-space-size=2048` | V8 堆上限（生产建议 2-4GB）|
| `BIOCORE_OOM_THRESHOLD_MB` | `auto` | OOM watchdog 阈值；超过 graceSamples 次后 SIGTERM（生产模式）|
| `BIOCORE_OOM_GRACE_SAMPLES` | `3` | 连续 N 次采样超阈值才触发，避免瞬时尖刺误判 |
| `BIOCORE_DIAGNOSTIC_DUMP_DIR` | `./crashes` | 崩溃诊断包目录（Docker 中映射到 host volume）|
| `BIOCORE_DIAGNOSTIC_KEEP_LAST` | `50` | 保留最近 N 个诊断包，超出删最早 |
| `BIOCORE_EVENT_BUFFER_SIZE` | `1000` | SSE Last-Event-ID 重放 buffer 上限 |
| `BIOCORE_SSE_MAX_CLIENTS` | `100` | /api/v1/events 并发连接上限（防 FD 耗尽）|
| `BIOCORE_NOTIFIER_THROTTLE_MIN` | `5` | 通知防抖窗口（分钟）|
| `BIOCORE_METRICS_REQUIRE_AUTH` | `false` | `/api/v1/admin/metrics` 是否要求 admin（默认开放给 Prometheus 标准 scrape）|

## 12. Recipe DAG 运行时（v1.7.0+）

### 12.1 老 v1 配方兼容
所有 dag_schema_version=1 配方启动时由 `linearToDag()` 内存转换为 DAG，运行时统一走 DAGExecutor。无需手动迁移；老配方行为与 v1.6.0 完全一致。

### 12.2 v2 配方 branch 节点
- 编辑器 `/recipes/:id/edit-v2` 画 IF/ELSE 节点 + 表达式（如 `OD600 > 5`）
- 升级 v1.7.0 后自动启用，无 feature flag
- 表达式可用字段：`temperature` / `pH` / `DO` / `OD600` / `weight` / `phase_elapsed_min`
- 运算符：`>` `<` `>=` `<=` `==` `!=` `+` `&&` `||` + 括号

### 12.3 default_branch 兜底
PV 缺失（如 OD600 还没采到）时 branch 求值会失败。在编辑器中可选 `default_branch: 'true' | 'false'` 兜底。

### 12.4 升级前提
**必须无 running 批次**。把所有反应器停到 idle 后再升级。

### 12.5 数据库迁移
- migration 023：`batches.current_node_id TEXT` + `audit_logs.target_kind TEXT`（自动应用，O(1) ALTER ADD COLUMN）

### 12.6 API 变化
- 路由：`/reactors/:reactorId/phases/:phaseRef/{start,hold,skip,restart}` 现在接受 nodeId 字符串。数字 phaseRef 在 T24 后已废止，请用 nodeId（如 `n_3`）。
- WS payload：`payload_version: 2`，含 `node_id` 字段。

## 13. SP-PLC-3 Phase 3c — Redis + reliable queue 配置（v1.19.0+）

Phase 3c 引入 Redis pub/sub 实现多 server 实例 TagCache 共享 + ws_message_queue
sqlite 可靠投递 + client ack 机制，支持横向扩展部署。

### 13.1 Redis（opt-in）

| 变量 | 默认 | 说明 |
|---|---|---|
| `REDIS_URL` | （空） | 空 = 单实例模式（等价 Phase 2 行为，无 cross-instance 同步）；设为 `redis://host:6379` 启用 Redis. 兼容 cluster / sentinel / standalone（ioredis）|
| `SERVER_ID` | 启动期生成 UUID | 多实例部署建议固定 env，便于审计 + Redis pub/sub 自回环识别 |

启动日志关键检查项：
- `[redis-client] connected` — Redis TCP 连接 OK
- `[redis-cache-sync] serverId=<uuid> mode=redis` — 跨实例同步桥启动 OK
- `[ws-msg-queue] dispatcher started (tick=500ms ackTimeout=5000ms maxRetries=3)` — 可靠投递 dispatcher 启动

### 13.2 多实例部署 — 必须配 sticky session

Phase 3c **不实现** 跨 server WebSocket 转发（plan §1 Q10 决策），需在 LB 层做
ws connection 粘性分配，否则同 client 重连可能落到不同 server 导致 subscription
状态丢失。

nginx ip_hash 示例：

```nginx
upstream biocore_backend {
  ip_hash;
  server biocore-s1:3001;
  server biocore-s2:3001;
}

server {
  listen 443 ssl;
  location /ws {
    proxy_pass http://biocore_backend;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_read_timeout 86400s;
  }
}
```

Caddy 等价（cookie-based sticky）：

```caddy
biocore.example.com {
  reverse_proxy /ws biocore-s1:3001 biocore-s2:3001 {
    lb_policy cookie biocore_sticky
  }
}
```

### 13.3 Hot-rollback env

任一开关 = `true` 时关闭对应功能，退回早期行为，便于生产急救：

| 变量 | 默认 | 设为 true 的效果 |
|---|---|---|
| `WS_QUEUE_DISABLED` | （空） | dispatcher 不启动，critical msg 仍入队但不发送（累积 pending）；hot-rollback 真正退回 Phase 2 best-effort 需配 ws-server 端 disable enqueue（暂未做开关） |
| `WS_ACK_DISABLED` | （空） | client 不发 ack（依赖前端实现）；server 始终等到 `WS_ACK_TIMEOUT_MS` 超时再 retry |
| `WS_ACK_TIMEOUT_MS` | `5000` | server 等 ack 超时（ms）。client RTT 大时调高，避免误重发 |
| `WS_QUEUE_RETRY_MAX` | `3` | dispatcher retry 次数上限，超即 `status='failed'` 终态 |

### 13.4 新增可观测指标（/api/v1/admin/metrics）

Phase 3c 在 §11 表基础上加 4 个 Prometheus metric：

| 指标 | 类型 | label | 说明 |
|---|---|---|---|
| `biocore_redis_connected` | Gauge | — | Redis 连接状态（1=connected, 0=disconnected / REDIS_URL 空）。30s 周期采样 |
| `biocore_redis_publish_total` | Counter | `channel` | redis-cache-sync publish 调用累计（label `channel=tagcache:write`）|
| `biocore_ws_queue_size` | Gauge | `status` | ws_message_queue 各状态 row 数（pending/dispatching/delivered/failed）。30s 周期采样 |
| `biocore_ws_ack_latency_seconds` | Histogram | — | client ack 端到端延迟（server send → server 收 ack），buckets `[0.01, 0.05, 0.1, 0.5, 1, 5]`（无 label）|

### 13.5 数据库迁移

- migration 041：新表 `ws_message_queue`（id PK, client_id, channel, payload JSON, status, retry_count, last_error, created_at, delivered_at + 2 index）。fresh DB 自动应用。

### 13.6 npm 依赖

- 新增 `ioredis ^5.4.0`（~3MB unpacked，0 native binding，TypeScript-first）

### 13.7 降级路径

| 场景 | 行为 |
|---|---|
| `REDIS_URL` 空 | initRedisClient 返 null → startRedisCacheSync 返 noop handle → 单实例模式（等价 Phase 2） |
| Redis 连不上 | console.error 报警，server 继续启动，cacheSyncHandle 仍为 noop → cache.write 仍工作，publish 不发出 |
| Redis 启动后中断 | publish 失败 console.error 吞，cache.write 不受影响；下次 PLC tick 再 publish 一次（pub/sub best-effort） |
| `WS_QUEUE_DISABLED=true` | dispatcher 不启动；ws_message_queue 行累积，重启后取消该 env 即恢复处理 |
